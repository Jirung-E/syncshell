# 아키텍처 불변식

프로젝트 전체의 하중을 지지하는 규범. 예광탄(C-002)에서 확정됐고, 예광탄이 끝난 뒤에도
계속 유효하다. 이후 모든 DEV 퀘스트는 이 규칙을 위반하지 않는지가 대조 기준이다.
"나중에 하면 비싼 것"을 지금 지키기 위한 목록이므로 예외는 별도 합의 없이 두지 않는다.

## 1. core는 egui/UI를 모른다

`syncshell-core` 크레이트(PTY, 파일시스템, 동기화 상태, 경로 처리)는 렌더링 계층을
참조하지 않는다. `syncshell-ui`만 egui/eframe에 의존한다.

**왜:** 여기가 새면 2단계(WSL)·3단계(Linux/macOS) 이식 비용이 통째로 돌아온다.
core가 UI 비의존이어야 헤드리스 스파이크(DEV-004 등)도 성립한다.

**검증됨(TR-006):** 예광탄 종료 시점에 `syncshell-core`의 Cargo.toml과 소스
전체를 grep으로 재확인 — egui/eframe 참조 없음.

## 2. 터미널 렌더러는 CJK 폭 2를 처음부터 처리한다

한글·한자·가나는 셀 폭 2. `unicode-width` 기반으로 그리드 좌표·커서 위치·선택 영역이
전부 이 폭을 반영해야 한다. 예광탄의 최소 렌더러(TR-002)부터 적용한다.

**왜:** 빠뜨리면 한글에서 커서가 어긋나고 선택 영역이 깨진다. 터미널 구현에서
가장 버그가 많이 나오는 지점이고, 한글 경로를 다루는 프로젝트라 이게 없으면
결과 자체를 눈으로 평가할 수 없다.

## 3. 영속 데이터 저장 위치는 `~/.syncshell/` 하나

세 플랫폼 동일 경로. 디렉터리 이름은 소문자.

```
~/.syncshell/
├── config.toml    ← 사람이 만지는 것 (셸, 폰트, 테마, 키바인딩)
└── state.toml     ← 앱이 덮어쓰는 것 (탭, 경로, 창 위치/크기)
```

- `directories` 크레이트나 XDG 3분할(config/state/cache)은 쓰지 않는다
- `SYNCSHELL_HOME` 환경변수로만 위치 오버라이드 가능 (포터블 실행·테스트용)
- **eframe 자체 persistence는 반드시 끈다** — 켜두면 `%APPDATA%` 등 플랫폼 기본 경로에
  우리가 모르는 두 번째 저장 위치가 생긴다
- 경로 해석은 `core`의 함수 하나로 격리한다 — 호출부가 경로를 직접 조립하지 않는다

**왜:** 설정과 세션 상태를 한 파일에 두면 앱이 종료할 때마다 파일을 통째로 재작성하면서
사용자가 손으로 만진 내용(주석 등)을 날린다. 저장 위치가 여러 곳으로 흩어지면
지원·디버깅이 어려워지고, "%APPDATA%에 몰래 뭔가 생긴다"는 신뢰 문제가 된다.

## 4. cwd 추적의 주 방식은 OSC 7

터미널의 현재 작업 디렉터리 추적은 셸이 뱉는 OSC 7 이스케이프 시퀀스를 주 방식으로 한다.
프로세스 cwd 폴링(PEB 읽기, `/proc/PID/cwd` 등)은 OSC 7 주입이 실패한 경우의
**로컬 한정 폴백**으로만 둔다.

**왜:** 폴링은 플랫폼마다 전부 다르고(Windows는 문서화 안 된 API, macOS는 권한 이슈)
2단계 WSL과 3단계 SSH 원격에서는 아예 불가능하다 — 다른 커널/다른 머신의 프로세스이기
때문이다. OSC 7은 파서 하나로 로컬·WSL·원격을 전부 커버한다.

## 5. PTY로 종료 감지는 read() EOF가 아니라 `try_wait()` 폴링

셸 프로세스 종료(예: `exit` 입력)를 감지할 때, PTY read()가 EOF(Ok(0))를
돌려주길 기다리면 안 된다. `portable_pty::Child::try_wait()`를 매 `pump()`
호출마다 논블로킹으로 폴링하는 것이 유일하게 신뢰할 수 있는 방법이다.

**왜:** ConPTY는 자식 프로세스가 종료돼도 master 쪽 read가 EOF를 신뢰성 있게
주지 않는다는 것을 실측으로 확인했다(`exit` 입력 후 5초를 기다려도 EOF 없음).
이걸 놓치면 셸은 죽었는데 앱은 무한정 살아있는 상태가 된다(TR-006에서 발견,
`exit` 쳐도 앱이 안 닫히던 버그의 원인).

## 6. PTY에 쓰는 줄 끝은 반드시 `\r` 하나

셸에 명령을 주입하거나(동기화의 cd 주입 등) 붙여넣기 텍스트를 전달할 때,
줄 끝은 `\r` 단독이어야 한다. `\r\n`을 쓰지 않는다 — 여러 줄 붙여넣기의 내부
개행(`\n`)도 전달 전에 `\r`로 정규화한다.

**왜:** 실제 키보드 Enter는 `\r`만 보낸다. `\r\n`을 쓰면 `\r`로 제출된 직후
남는 `\n`이 빈 줄에서 또 한 번의 Enter처럼 처리되어 PSReadLine이 줄 연속
프롬프트(`>>`)를 잘못 띄운다(TR-006에서 발견 — 초기화 스크립트 주입 시
첫 실행 화면이 지저분해 보이던 원인이었음).

## 7. 터미널 리사이즈는 반드시 최소 크기 하한을 강제한다

`TerminalSession::resize()`(또는 이를 대체하는 모든 리사이즈 경로)는 호출부가
넘긴 cols/rows 값을 그대로 믿지 말고, 안전한 최소값(현재 20컬럼×4행)으로
clamp해야 한다.

**왜:** 터미널을 극단적으로 좁은 컬럼 수(실측: 1컬럼)로 줄이면,
alacritty_terminal이 기존 스크롤백의 넓은 줄들을 그 폭으로 리플로우하려다
줄 수가 폭발적으로 늘어나 **~5GB 메모리 할당 시도 후 크래시**하는 것을 실측으로
확인했다(`STATUS_STACK_BUFFER_OVERRUN`). egui는 첫 프레임 등에서 위젯 rect를
일시적으로 아주 작게 보고할 수 있어, 이 clamp 없이는 실사용 중에도 트리거될
수 있다(TR-006에서 발견, "ls 결과가 잘리고 리사이즈해도 안 돌아옴" 조사 중
드러남).

## 8. 키보드 중심 위젯은 매 프레임 명시적으로 포커스를 잠가야 한다

터미널처럼 키 입력을 직접 PTY로 전달하는 위젯은, 매 프레임
`response.request_focus()` + `ui.memory_mut(|m| m.set_focus_lock_filter(id,
EventFilter { tab: true, horizontal_arrows: true, vertical_arrows: true,
escape: true }))`로 포커스와 해당 키들을 스스로 잠가야 한다.

**왜:** egui는 포커스를 가진 위젯이 하나도 없으면 Tab/화살표 키를 "다음
위젯으로 포커스 이동" 명령으로 자동 소비한다(egui 소스 `memory/mod.rs`
확인됨). 터미널이 포커스를 잠그지 않으면, Tab을 누를 때 포커스가 다른
패널(예: 파일 목록의 selectable_label)로 옮겨가고, 뒤이은 Enter가 "포커스된
위젯 활성화"로 해석되어 그 항목이 클릭된 것처럼 처리된다 — 터미널 자체는
Tab/Enter를 정상적으로 PTY에 전달하므로 "내가 타이핑한 것도 되고 엉뚱한
동작도 같이 일어난다"는 헷갈리는 증상으로 나타난다(TR-006에서 발견: "탭
치면서 탐색기쪽 폴더가 선택되고 엔터 치면 cd가 입력되어버림"). 새 인터랙티브
위젯(탭바, 커스텀 타이틀바 버튼 등)을 추가할 때도 이 상호작용을 염두에 둘 것.

**단, `request_focus()`는 포커스가 없을 때만 부른다(BUG-007).** egui의
`request_focus`는 부를 때마다 IME 조합 중단(`interrupt_ime`)을 같이 요청한다.
매 프레임 부르면 egui-winit이 매 프레임 IME를 껐다 켜서 한글 조합이 확정되기 전에
계속 취소된다(Windows 실측: 조합 글자가 잠깐 보였다 사라짐). 포커스 잠금 필터
(`set_focus_lock_filter`)는 매 프레임 거는 게 맞다 — 그건 IME와 무관하다.
