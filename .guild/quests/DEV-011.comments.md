## 예광탄에서 발견한 것 (TR-006 회고 반영)

지금은 맑은 고딕을 하드코딩 로드 중(시스템 폰트 폴백 체인 미구현, 이 퀘스트의
본래 범위). 그 상태로 실사용해보며 추가로 발견한 것:

**셀 폭을 문자 'M'의 폭으로 잡는데, 맑은 고딕은 완전한 monospace 폰트가
아니라서 'M'이 다른 라틴 문자보다 넓다.** 그 결과 실제 필요한 것보다 컬럼
수가 적게 계산됨 — 좁은 창에서 `Get-ChildItem`/`ls`의 기본 테이블 포맷이
컬럼(특히 파일명)을 드롭해버리는 문제(PowerShell 자체 동작)를 더 자주
겪게 만드는 요인 중 하나였다.

이 퀘스트에서 시스템 폰트 폴백 체인을 제대로 구현할 때, 셀 폭 기준 문자를
'M' 대신 더 일반적인 문자(예: '0'이나 실측 평균)로 바꾸거나, 실제 monospace
폰트를 우선 사용하는 것을 고려할 것.

## 참고 — 별개로 논의된 개선안 (보류)
"창 크기와 무관하게 넓은 출력이 다 보이게" 요청에 대해 두 가지 옵션을
검토했으나 사용자가 지금은 보류하기로 함:
- `ls`/`dir` 전용 `-Wrap` 별칭 세션 주입 (작고 빠른 개선)
- PTY 폭과 렌더링 폭 분리 + 가로 스크롤 (근본적, 더 큰 작업)
필요해지면 이 퀘스트 또는 DEV-009(레이아웃) 근처에서 진행.

## 셀 폭 기준 문자 수정 (DEV-016 자간 문제와 동일 근본 원인)

`terminal_widget.rs`의 `cell_size()`가 셀 기준폭을 라틴 문자 'M' 대신
**한글 한 글자 폭의 절반**으로 잡도록 변경했다.

## 근거
CJK 글자는 폰트 안에서 전부 동일한 고정 폭이라는 강한 타이포그래피 요구사항이
있다(WIDE_CHAR 셀은 렌더러에서 정확히 기준폭의 2배로 그려짐). 반면 'M'은
완전한 monospace가 아닌 폰트(맑은 고딕)에서 다른 라틴 문자보다 훨씬 넓게
그려지는 경향이 있다.

## 효과 (실측)
같은 1400px 폭에서 계산되는 컬럼 수가 **95 → 175로 거의 2배** 늘었다
(`realistic_frame_loop_keeps_stable_cols_and_wraps_wide_output` 테스트로 확인).
이건 DEV-016(자간이 넓어 보이던 문제)과, 이전에 발견했던 "좁은 창에서
`Get-ChildItem`의 이름 컬럼이 드롭되던 문제"(TR-006) 둘 다에 직접 도움이 된다 —
같은 근본 원인이었다.

## 검증
- `cargo test -p syncshell-ui`: 4개 전부 통과 (컬럼 수 안정성, wrap 정상,
  포커스 고정, 붙여넣기 전부 회귀 없음 재확인)
- `cargo test -p syncshell-core`: 16개 전부 통과

## 남은 것 (이번 패스에서 다루지 않음)
이 퀘스트의 본래 큰 범위 — **시스템 폰트 로딩 + 코드포인트별 폴백 체인**
(맑은 고딕에 없는 글리프를 다른 시스템 폰트에서 찾아오는 것), 글리프 아틀라스
캐싱, 사용자 폰트 설정(패밀리/크기) — 은 여전히 미구현. 이건 "자간이 넓다"는
보고와는 다른 문제(글자가 아예 두부로 나오는 것)라 별도 작업으로 남겨둔다.
`testing`으로 옮기지 않고 `Open`으로 유지 — 이번에 고친 건 이 퀘스트의
일부(셀 폭 기준)일 뿐, 전체 범위는 그대로 남아있어서.

## 글자 겹침 버그 수정 (이 퀘스트 남은 범위 중 일부 진행)

사용자 실사용 피드백: "터미널에서 글자가 겹쳐서 출력되는중".

## 원인

지난 패스에서 셀 폭 기준을 'M' → 한글 글자 폭의 절반으로 바꿨는데
(자간이 넓어 보이던 DEV-016 문제 해결용), 이게 **맑은 고딕이 완전한
monospace 폰트가 아니라는 사실**을 놓치고 있었다. 실측(16pt 기준):

| 글리프 | 폭(px) |
|---|---|
| 가(한글) | 16.0 |
| M | 14.67 |
| W | 15.26 |
| A | 10.53 |
| . | 3.5 |
| i / l | 3.94 |

셀 폭 기준(한글 폭의 절반=8.0)보다 넓은 라틴 글리프('M', 'W', 'A' 등 — 사실상
대부분의 라틴 문자)가 자기 칸을 넘어 다음 칸을 침범해서 그려졌다. 자간이
좁아 보이던 것(DEV-016)과 컬럼 드롭 문제(DEV-003/011 조사)는 개선됐지만,
그 대가로 실사용 텍스트(영문 명령어, 경로, 출력)의 상당수가 겹쳐 보이게
된 것 — 트레이드오프를 놓친 회귀였다.

## 수정 — 이 퀘스트의 원래 남은 범위(시스템 폰트 + 폴백 체인)로 해결

`install_font()`에 **Consolas**를 Monospace 1순위로 추가했다. 실측 결과
Consolas는 라틴 글리프 전부가 정확히 동일한 폭(16pt에서 전부 8.796875px)인
진짜 monospace 폰트다. 한글은 Consolas에 없으므로(글리프 폭 0으로 확인)
맑은 고딕을 그 뒤에 폴백으로 둔다 — egui가 코드포인트별로 폰트 커버리지를
보고 자동으로 알맞은 폰트를 골라 그린다(요청받은 "코드포인트별 폴백 체인"의
최소 실동작 버전).

`cell_size()`도 기준 글리프를 다시 'M'으로 바꿨다 — 이제 Consolas가 1순위라
'M'이 실제로 모든 라틴 문자를 대표하는 안전한 기준이 됐다(예전엔 맑은 고딕이
1순위였을 때만 'M'이 위험했던 것).

한글(맑은 고딕 폴백)은 자연 폭이 16px인데 셀 2칸(Consolas 8.796875 × 2 =
17.59px) 폭으로 그려져 아주 살짝 여백이 생긴다 — 겹침(overflow)이 아니라
여백(underflow) 방향이라 안전한 쪽이고, 육안상 문제되는 수준은 아니다.

## 검증
- `cargo test -p syncshell-ui`: 5개 전부 통과(스크롤백 테스트 포함, 회귀 없음).
- `cargo test -p syncshell-core`: 19개 전부 통과.
- `cargo build --workspace`: 클린 빌드.
- 실측 진단 테스트(임시)로 Consolas 라틴 전체 폭이 8.796875px로 균일함, 한글은
  0(미지원)임을 직접 확인 후 코드에 반영.

`testing`으로 유지 — 실제 화면에서 겹침이 사라졌는지는 사용자 확인 필요.
아직 남은 것: 코드포인트 폴백을 Consolas+맑은 고딕 두 개로만 좁게 처리함
(이모지, 기타 특수기호 등은 여전히 커버 안 될 수 있음), 사용자 폰트 설정
(패밀리/크기)은 여전히 미구현.

## 하드코딩 되돌리고 원래 방침대로 재구현

사용자 지적: "시스템 기본 문자 가져오게 하는 계획 아니였음?" — 맞는 지적이었다.
직전 커밋에서 글자 겹침 버그를 고치면서 `C:\Windows\Fonts\consola.ttf`,
`malgun.ttf`를 코드에 경로로 하드코딩했는데, 이건 이 퀘스트가 명시적으로
폐기한 접근("CJK 폰트를 번들하는 안은 폐기")을 그대로 재현한 것이었다.

## 재구현

새 모듈 `crates/syncshell-ui/src/font_fallback.rs` — `fontdb` + `ttf-parser` 사용.

- **주 폰트(라틴 고정폭)**: 파일 경로가 아니라 **이름**으로 시스템에 질의한다
  (`Cascadia Mono` → `Consolas` → `Cascadia Code` → `Courier New` 순, 첫 매치
  사용). 시스템에 하나도 없으면 fontdb 자체 기본값(Courier New)으로 자연히
  떨어진다 — Windows는 이 폰트를 항상 갖고 있어서 사실상 "번들 없는 최후
  폴백" 역할을 한다.
- **코드포인트별 폴백 체인**: `TerminalWidget::show()`가 매 프레임 화면에 그릴
  글자들을 스캔해서(`ensure_covers`), 지금 로드된 폰트로 못 그리는 글자가
  있으면 시스템 폰트 전체(`db.faces()`)를 훑어 그 글리프를 가진 폰트를
  찾는다(`ttf_parser`로 실제 cmap 조회) — 고정폭 우선, 없으면 아무거나. 찾으면
  그 자리에서 egui에 동적으로 등록한다. 한글이든 일본어든 이모지든 특정
  언어를 코드에 미리 얹어두지 않고 전부 이 경로로 처리된다.
- 이미 처리한 글자는 `HashSet<char>`로 캐싱해서 매 프레임 재스캔하지 않는다.

## 도중에 잡은 버그 2개

1. **`egui::Context::set_fonts()`는 "다음 pass부터" 적용된다**(공식 문서 그대로).
   `ensure_covers`가 폰트를 새로 등록해도 같은 프레임 안에서 바로 그릴 수는
   없다 — `request_repaint()`로 한 프레임 더 돌려서 다음 프레임부터 정상
   렌더링되게 처리했다(그 사이 한 프레임 두부로 보일 수 있지만 크래시 없음).
   테스트에서도 이걸 놓쳐서 `has_glyph` 검사가 옛 폰트 상태를 보고 있었던
   버그를 잡았다(`step_frame` 헬퍼 추가).
2. **시스템 폰트 전체 스캔(`load_system_fonts()`)을 인스턴스마다 새로 하면
   느리다.** 처음엔 `TerminalWidget`(→`FontFallback`) 인스턴스마다 각자
   스캔하게 했는데, 테스트에서 여러 인스턴스가 동시에 스캔하느라 실제 셸
   응답까지 밀려서 무관한 테스트(붙여넣기, 스크롤백, wrap)가 줄줄이
   실패했다 — `std::sync::OnceLock`으로 프로세스당 한 번만 로드해 공유하도록
   고쳤다(`shared_db()`). 앱 자체는 `TerminalWidget`이 하나뿐이라 원래도
   문제는 아니었겠지만, 설계상으로도 시스템 폰트 목록은 프로세스 전역
   자원이 맞다.

## 검증
- `font_fallback.rs`에 테스트 3개 신설: 주 폰트가 실제 monospace인지, 한글처럼
  주 폰트에 없는 글자가 `ensure_covers`로 실제 커버되는지(진짜로 시스템에서
  찾아서 등록하는지 — 특정 폰트를 미리 심어두지 않고 검증), 같은 글자를
  반복 요청해도 재스캔 안 하는지.
- `cargo test -p syncshell-ui`: 8개 전부 통과(스크롤백/붙여넣기/wrap 등
  기존 회귀 없음 재확인).
- `cargo test -p syncshell-core`: 19개 전부 통과.
- `cargo build --workspace`: 클린 빌드.

## 남은 것 (퀘스트 원래 범위 중 여전히 미구현)
- 글리프 아틀라스 캐싱 최적화(지금은 egui 기본 아틀라스에 의존)
- 사용자 폰트 설정(패밀리·크기·라인 하이트)
- 새 코드포인트를 만날 때마다 시스템 폰트 전체를 동기적으로 스캔한다 —
  드문 글자가 연달아 여러 개 나오면 그 프레임들에서 약간의 지연이 있을 수
  있다(백그라운드 스캔/비동기화는 안 함). 실사용에서 체감되면 별도로 다룰 것.

`testing` 유지 — 실제 화면에서 겹침 없이 잘 나오는지, 한글도 정상 표시되는지
확인 필요.

## 사전 스캔 매 프레임 실행 → 변경 시에만 실행

사용자 지적: "매 프레임 확인하는건 매우 비효율적인거 아닌지?" — 맞는 지적이었다.

## 실측

`SYNCSHELL_SCAN_TIMING` 임시 계측으로 재보니, 화면 170x48(8160셀) 기준
**사전 스캔만 프레임당 0.5~1ms**였다. 같은 조건에서 `show()` 전체가 3.66ms
(디버그 빌드)였으니 **스캔이 프레임 비용의 15~25%**를 먹고 있었다.

문제는 이게 거의 전부 낭비였다는 점이다 — 화면 내용이 안 바뀐 프레임에서도
매번 8160셀을 훑고 String을 새로 할당하고 글자마다 HashSet을 조회했다.
실사용에서는 "아무것도 안 바뀐 프레임"이 절대다수다.

## 수정

`TerminalSession`에 `content_version: u64` 추가 — PTY 바이트를 실제로 처리할
때마다(= 화면 내용이 바뀔 때만) 증가한다. `content_version()`으로 노출.

`TerminalWidget`은 `last_scan_key: Option<(u64, usize, u16, u16)>`를 들고
있다가, `(content_version, display_offset, cols, rows)`가 지난 프레임과
같으면 스캔을 통째로 건너뛴다. 화면에 보이는 글자가 바뀌는 경우는 이 셋뿐이다:

1. 셸이 새 출력을 냄 → `content_version` 증가
2. 스크롤 위치가 옮겨짐 → `display_offset` 변경
3. 창 크기가 바뀌어 보이는 셀 범위가 달라짐 → `cols`/`rows` 변경

## 검증

벽시계 시간이 아니라 "스캔을 실제로 몇 번 돌렸는지"로 검증한다(빌드 모드나
머신 부하에 안 흔들리게) — `scans_run()` 카운터 추가.

`font_scan_is_skipped_when_screen_content_unchanged`:
- 조용한 100프레임 동안 실제로 돈 스캔 횟수 = **0** (기존엔 100)
- 반대 방향도 검증: 새 출력(`Write-Host '새출력 テスト'`)이 오면 반드시 다시
  스캔한다 — 안 그러면 새 글자가 영영 두부로 남는다.

측정으로도 확인: `show()` 전체가 3.66ms → 3.24ms (스캔분 제거됨). 남은
3.24ms는 8160셀을 실제로 그리는 draw 루프이고 디버그 빌드 특성이다.

## 덤: 유휴 시 다시 그리기 확인

같이 물어본 "정지화면일 때도 프레임을 갱신하고 있는 건 아닌지"도 테스트로
확인했다 — `idle_frames_do_not_request_continuous_repaint`.

egui의 `ViewportOutput::repaint_delay`가 유휴 상태에서 `Duration::MAX`
(= "입력이 올 때까지 다시 그릴 필요 없음")로 나오는 것을 확인. 즉 유휴 시
프레임을 안 돌린다. 다시 그리기를 요청하는 경로는 넷뿐이고 전부 이벤트
기반이다: PTY 데이터 도착, 파일시스템 워처 이벤트, cwd 디바운스 타이머,
폰트 폴백이 새 폰트를 등록했을 때(이제는 화면이 바뀐 프레임에서만).
