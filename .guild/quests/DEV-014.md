커스텀 타이틀바와 창 크롬을 구현한다. (탭바를 타이틀바에 통합하기 위해 필요)

## 플랫폼별 방침 — 네이티브 버튼 유지 여부

| 플랫폼 | 방침 |
|---|---|
| **macOS** | **네이티브 유지.** winit의 투명 타이틀바 + fullsize content view로 네이티브 신호등 버튼이 콘텐츠 위에 뜨는 형태. VS Code·Zed가 쓰는 표준 패턴 |
| **Windows** | **직접 그린다.** 장식을 끄면 버튼도 사라지고, 네이티브 버튼을 남기려면 HWND를 받아 `WM_NCCALCSIZE`/`WM_NCHITTEST`를 직접 처리해야 함. 비용 대비 이득이 적음 |
| **Linux** | **직접 그린다.** GNOME 계열은 앱이 직접 그리는 CSD가 표준이라 "네이티브 버튼" 개념이 약함 |

즉 macOS만 네이티브, 나머지는 자체 렌더링. 대부분의 크로스플랫폼 에디터가 취하는 구성.

## 범위
- 자체 최소화/최대화/닫기 버튼 (호버·프레스 상태, 플랫폼별 배치 — Windows는 우측, macOS는 좌측)
- **드래그 영역 히트테스트** — 빈 영역을 잡으면 창이 끌리도록
- 더블클릭 최대화/복원
- 최대화 시 창이 화면 밖으로 잘리는 문제 보정
- 창 가장자리 리사이즈 핸들 (장식을 끄면 이것도 직접 처리해야 함)

## Windows 11 스냅 레이아웃 (놓치기 쉬움)
최대화 버튼에 호버하면 뜨는 분할 배치 플라이아웃은 `WM_NCHITTEST`에서 **`HTMAXBUTTON`을
반환할 때만** 나타난다. 직접 그린 버튼이면 해당 좌표에서 이 값을 수동으로 응답해야 하고,
빠뜨리면 Win11 사용자가 즉시 이질감을 느낀다. 개발자 도구에서는 체감이 큰 부분.

## 메모
- winit의 정확한 API 표면(투명 타이틀바 옵션명 등)은 구현 시점의 버전에서 확인할 것
- Windows 쪽 `WM_NCHITTEST` 처리는 `raw-window-handle`로 HWND를 얻어 서브클래싱

## Test plan
- 세 플랫폼에서 창 이동·리사이즈·최대화·복원·닫기 정상 동작
- Windows 11에서 최대화 버튼 호버 시 스냅 레이아웃 플라이아웃 표시
- macOS에서 신호등 버튼이 콘텐츠와 겹치지 않고 정상 위치에 표시
- 최대화 상태에서 콘텐츠가 잘리지 않는지
- 멀티 모니터 / 서로 다른 DPI 환경에서 좌표 계산 정확한지
