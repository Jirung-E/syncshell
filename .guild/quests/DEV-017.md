탐색기 우클릭 메뉴에서 **윈도우 셸 확장 항목**(7-Zip, Git, TortoiseSVN, 백신 검사 등
사용자가 설치한 프로그램이 등록한 항목)까지 띄운다.

## 배경
DEV-008에서 컨텍스트 메뉴를 직접 구현했다(열기·터미널에서 열기·경로 복사·이름
바꾸기·삭제·새 폴더). 이건 `trash`/`open` 크레이트 기반이라 2·3단계 WSL/Linux/macOS
에서 그대로 살아남지만, **셸 확장 항목은 안 나온다** — 그건 Windows 셸이 COM으로
들고 있는 것이라 우리가 재현할 수 없다.

사용자가 "시스템 파일탐색기에서처럼"을 요청했을 때 확인한 결론: 직접 만든 메뉴를
먼저 하고, 셸 메뉴 연동은 이 퀘스트로 분리한다(2026-07-29).

## 범위
- `IShellFolder::GetUIObjectOf`로 대상 항목의 `IContextMenu` 획득
- `IContextMenu::QueryContextMenu`로 HMENU 채우고 `TrackPopupMenu`로 표시
- 선택 결과를 `IContextMenu::InvokeCommand`로 실행
- `IContextMenu2`/`IContextMenu3`의 `HandleMenuMsg` 처리 (서브메뉴·소유자 그리기 항목)
- 직접 만든 메뉴에 **"추가 옵션 표시"** 항목으로 진입점 제공
  (Windows 11 탐색기가 셸 확장을 접어두는 방식과 같은 배치)
- 다중 선택 상태에서의 호출

## 설계 제약
- **Windows 전용 코드다.** `#[cfg(windows)]`로 격리하고, 다른 플랫폼에서는 이
  메뉴 항목 자체가 안 보이게 한다. 직접 만든 메뉴의 동작에는 영향을 주지 않아야 한다.
- architecture 규칙(core는 UI/플랫폼을 모른다)에 따라 `syncshell-core`에 넣지 않는다.
  UI 크레이트의 Windows 전용 모듈로 둔다.
- DEV-008이 명시한 "플랫폼 API 직접 호출 금지"는 **파일 조작**(휴지통·열기)에 대한
  방침이다. 이 퀘스트는 그 방침의 예외가 아니라 다른 축 — 조작 자체는 여전히
  셸이 하고 우리는 메뉴를 위임할 뿐이라, 크로스플랫폼 대체재가 존재하지 않는다.

## 미해결
- egui는 자체 렌더링이라 네이티브 HMENU를 앱 창 위에 띄우는 게 자연스러운지
  확인 필요(별도 네이티브 팝업 창이 뜨는 형태가 될 가능성). 착수 시 최소
  스파이크로 먼저 검증할 것.
- `windows` 크레이트(공식 바인딩) 의존이 추가된다. 빌드 시간·바이너리 크기 영향 확인.

## Test plan
- 7-Zip 등 셸 확장이 설치된 환경에서 해당 항목이 실제로 뜨고 동작하는지
- 셸 확장이 하나도 없는 깨끗한 환경에서 크래시 없이 기본 항목만 뜨는지
- 메뉴 표시 중 앱이 멈추지 않는지(모달 루프 처리)
- 폴더/파일/다중선택 각각에서 동작
