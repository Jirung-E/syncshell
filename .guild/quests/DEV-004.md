터미널의 현재 작업 디렉터리(cwd)를 실시간 추적하는 방식을 **헤드리스 테스트 바이너리로** 검증한다.

## 왜 최우선인가
프로젝트의 가치는 터미널 렌더러가 아니라 **동기화**에 있고, 그 동기화가 성립하는지는
전적으로 cwd 추적이 실용적으로 되느냐에 달려 있다. 여기서 결론이 안 나면 DEV-006 설계가
통째로 뒤집힌다. **UI 코드를 한 줄도 쓰기 전에 이것부터 끝낸다.**

## 헤드리스로 하는 이유
GUI가 전혀 필요 없다. DEV-002의 PTY 레이어만 있으면 된다 —
PTY 띄우고 → `cd` 입력하고 → 감지된 cwd를 stdout에 찍는 콘솔 바이너리로 충분하다.
UI 스택 선택과 무관하게 검증되고, 그만큼 빨리 답이 나온다.

## 방침: OSC 7을 주 방식으로 확정
당초 "OSC 7 vs 프로세스 폴링" 저울질로 잡았으나, 크로스플랫폼을 전제하면 결론이 정해진다.

- **폴링은 플랫폼마다 전부 다르고 전부 지저분하다** — Linux는 `/proc/PID/cwd`,
  macOS는 `proc_pidinfo(PROC_PIDVNODEPATHINFO)`(권한 이슈), Windows는
  `NtQueryInformationProcess`로 PEB 읽기(문서화 안 된 API)
- **결정적으로, 2단계 WSL과 3단계 SSH 원격에서는 폴링이 아예 불가능하다.**
  다른 커널/다른 머신의 프로세스이기 때문. OSC 7만 살아남는다
- OSC 7은 셸이 뱉는 표준 이스케이프 시퀀스라 **파서 하나로 전 플랫폼·원격까지 커버**

따라서 폴링은 "OSC 7 주입이 실패한 경우의 로컬 한정 폴백"으로 격하한다.

## 검증할 것 (스파이크의 실제 질문)
1. **셸 프로파일을 건드리지 않고 OSC 7을 주입하는 방법** — 이게 핵심 난제
   - PowerShell: `prompt` 함수 재정의를 실행 인자로 주입 가능한가 (`-NoExit -Command`?)
   - 사용자의 기존 `$PROFILE`을 깨뜨리지 않고 덧붙이는 방법
   - cmd: `PROMPT` 환경변수로 ESC 시퀀스 삽입이 되는가
   - bash/zsh: `PROMPT_COMMAND` / `precmd` 주입
2. 주입 실패를 어떻게 감지하고 폴백으로 넘어갈 것인가
3. 서브셸·중첩 셸·ssh 세션에서의 동작 한계 (어디까지 포기할지 명시)

## Test plan
- PowerShell / cmd / pwsh 각각에서 `cd` 후 cwd가 정확히 감지되는지
- 사용자가 이미 커스텀 프롬프트(oh-my-posh 등)를 쓰는 환경에서 깨지지 않는지
- 심볼릭 링크, UNC 경로, 공백/한글 포함 경로에서 정상 동작
- 폴백 경로(폴링) 동작 및 CPU 사용량 측정
- **산출물: 어느 방식으로 갈지 결론 + 각 셸별 주입 스니펫을 퀘스트 댓글로 기록**
