# 스파이크 결론

`portable-pty`로 PowerShell/cmd.exe를 실제로 띄워 OSC 7 주입 → cwd 감지 왕복을
헤드리스로 검증했다. 코드는 스파이크 규칙대로 버렸다(재현 방법은 하단 스니펫 참고).

## 결론: OSC 7 확정, 프로파일 파일 불필요

**주입 방식은 "PTY 기동 직후, 사용자가 타이핑하듯 스크립트를 쓰고 Enter."**
`-Command` CLI 인자로 넘기는 방식(따옴표 이스케이프 지옥)도, `$PROFILE` 파일을
수정하는 방식(사용자 설정을 건드림)도 아니다. PTY에 쓰는 바이트는 셸이 실제
키 입력과 구분하지 못하므로, 함수 정의 같은 멀티 토큰 스크립트도 그대로 먹는다.

**지연 없이 즉시 써도 안정적으로 처리된다.** spawn 직후 sleep 없이 바로 써봤고
(cmd.exe는 16ms, PowerShell은 초기 로딩 때문에 조금 더 걸림) 3회 반복 모두 정상
동작했다. OS가 자식 프로세스의 stdin을 버퍼링하므로 "첫 프롬프트를 기다렸다가
주입" 같은 타이밍 로직은 불필요 — TR-005에서 패널이 열리자마자 초기 cwd를
알아야 하는 요구와 직결되는 부분이라 확인해둘 가치가 있었다.

## 셸별 주입 스니펫 (검증됨)

**PowerShell 5.1** — `prompt` 함수를 재정의해 프롬프트 그릴 때마다 OSC 7을 먼저 뱉게 함:
```powershell
function prompt {
  $p = (Get-Location).Path
  $u = "/" + ($p -replace '\\','/')
  Write-Host -NoNewline ([char]27 + "]7;file://" + $env:COMPUTERNAME + $u + [char]7)
  return "PS " + $p + "> "
}
```

**cmd.exe** — `PROMPT` 환경변수. cmd는 `$E`를 ESC(0x1B)로 해석하는 자체 메타 코드가
있어서 raw 이스케이프 바이트를 직접 넣을 필요가 없다:
```cmd
set PROMPT=$E]7;file://%COMPUTERNAME%/$P$E\$G
```
(`$P`=현재 드라이브+경로, `$G`=`>`. `%COMPUTERNAME%`은 `set` 실행 시점에 먼저
치환되고 `$P`/`$G`/`$E`는 cmd 전용 코드라 그대로 남는다.)

**pwsh 7** — 이 머신에 설치돼 있지 않아 직접 검증은 못 했다. `prompt` 함수
재정의 메커니즘은 Windows PowerShell 5.1과 동일하므로 위 스니펫이 그대로
동작할 것으로 예상하나, **미검증**. pwsh를 기본/선택 셸로 지원하기 전에
한 번은 실기 확인 필요.

## 검증한 것 (전부 PASS, 3회 반복 재현)
- 기본 `cd` (상대/절대), `cd ..`
- **한글 + 공백 포함 경로** 왕복 정확 (`C:\Users\...\dev004 테스트 폴더`)
- **응답을 기다리지 않고 두 `cd`를 연달아 주입**(TR-005의 "폴더 빠르게 두 번
  클릭" 상황 재현) — 두 감지 이벤트가 순서대로 깨끗하게 분리돼 들어왔고,
  최종 상태도 정확했다. "마지막 감지값이 승리" 전략을 SyncState 설계에
  그대로 써도 된다는 근거가 됐다.

## ⚠ TR-004 전제 정정 — alacritty_terminal은 OSC 7을 처리하지 않는다

TR-004 퀘스트 본문에 "alacritty_terminal이 OSC를 이미 파싱하므로 거기서
훅을 잡을 수 있는지 확인"이라고 적어뒀는데, **확인 결과 틀렸다.**

`alacritty_terminal 0.24.2`(내부적으로 `vte 0.13.1`의 `osc_dispatch`를 사용)의
OSC 처리 match 문에는 `b"7"` 분기가 없다. 인식 못 하는 OSC 커맨드 번호는
`unhandled()` 함수로 가서 `debug!` 로그만 찍고 버려진다 — `Handler` trait에도,
공개된 `Event` enum(Title/ClipboardStore/ColorRequest/PtyWrite/Bell/Exit 등)
에도 cwd 관련 variant가 전혀 없다. 소스로 직접 확인함(경로:
`vte-0.13.1/src/ansi.rs` `fn osc_dispatch`, 최종 `_ => unhandled(params)`).

**다행히 안전하게 무시된다.** vte의 상태 기계는 인식 못 하는 OSC 커맨드 번호여도
OSC 문자열 모드 자체는 정상적으로 진입/종료 처리하므로, OSC 7 바이트가 화면에
깨진 문자로 새지는 않는다. 즉 **같은 PTY 바이트 스트림을 alacritty_terminal에도
그대로 먹이면서, 별도로 우리 자체 OSC7 스캐너에도 그대로 태핑**하면 된다 —
스트림을 필터링하거나 분기할 필요 없음.

**TR-004는 이 스파이크에서 검증한 것과 같은 방식의 소형 OSC7 스캐너를 직접
구현해야 한다** (vte를 포크하거나 훅을 찾는 게 아니라). 필요한 로직은 단순하다:
바이트를 버퍼에 누적 → `ESC ] 7 ;` 탐색 → 그 뒤로 터미네이터(`BEL` 또는
`ESC \`) 탐색 → 사이 payload 추출 → `file://<host>/<path>` 에서 path만
취하고 퍼센트 디코딩. 스캐너 자체는 알고리즘 난도가 낮고(스파이크에서
~60줄), alacritty_terminal 통합과 독립적으로 짤 수 있다.

## 감수한 한계 / 후속 확인 필요
- **퍼센트 인코딩을 하지 않았다.** 스파이크의 PowerShell/cmd 스니펫은 경로를
  URI 스펙대로 percent-encode하지 않고 날것으로 넣는다. 이번 테스트 범위
  (한글+공백)에서는 문제없었지만, 경로에 `%`나 `#`(URI fragment 구분자)가
  있으면 파싱이 깨질 수 있다. **TR-004에서는 주입 스크립트에 percent-encode를
  넣고, 스캐너 쪽에서 percent-decode하는 걸 기본으로 할 것.**
  (스캐너 쪽 percent-decode 자체는 스파이크에도 이미 구현해봤고 어렵지 않다.)
- **oh-my-posh 등 커스텀 프롬프트와 공존 문제는 미해결.** 이 방식은 `prompt`
  함수를 통째로 덮어쓴다. 커스텀 프롬프트를 쓰는 사용자는 syncshell 안에서
  프롬프트 모양이 바뀌어 보인다. TR-004 범위에서는 허용하고 넘어가되(당초
  DEV-004 계획에도 "커스텀 프롬프트 사용자 배려는 예광탄 이후"로 돼 있었음),
  1단계 완전판(DEV-006)에서는 기존 `prompt` 함수를 감싸서 체이닝하는 방식을
  검토해야 한다.
- **UNC 경로, 심볼릭 링크, 중첩 셸(서브셸)은 이번 스파이크에서 테스트하지
  않았다.** 시간 대비 우선순위 판단으로 스코프에서 뺐다. `$P`/`Get-Location`이
  이런 경로도 문자열로 그대로 뱉을 가능성이 높아 위험도가 낮다고 보지만,
  TR-004~DEV-006 구현 중 실제 프로젝트 경로로 한 번은 확인 필요.
- **폴링 폴백은 이번에 구현/측정하지 않았다.** OSC 7이 확정 주 방식이 됐고
  당장 폴백이 필요한 실패 사례를 못 만나서, CPU 사용량 측정은 실제로 폴백이
  필요해지는 시점(TR-004/DEV-006 구현 중 주입 실패 케이스 발견 시)으로 미룬다.

## 재현 방법 (필요 시)
`portable-pty`로 PTY 열고 위 두 셸을 각각 spawn → 셸별 스니펫을 쓰고 Enter →
`cd` 명령들을 순서대로 주입하며 출력 바이트에서 위 스캐너로 OSC7 추출 →
기대 경로와 비교. 3회 반복 전부 PASS. 이 코드 자체는 스파이크 규칙에 따라
저장소에 남기지 않았다(위 스니펫 재현으로 충분).
