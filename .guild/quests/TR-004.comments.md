## 구현 완료 — 자동 검증 결과

`syncshell-core`에 `osc7.rs`(스캐너 + 퍼센트 인코딩 왕복) + `terminal.rs` 통합
(PowerShell 기동 시 즉시 주입, 같은 바이트 스트림을 osc7 스캐너와 alacritty_terminal에
동시 태핑, `TerminalSession.cwd` 필드로 최신 감지값 노출).

### 자동 테스트
- `cargo test -p syncshell-core`: osc7 파서 유닛 테스트 4개(기본 경로, 한글+공백+특수문자
  퍼센트 인코딩 왕복, 여러 read()에 걸쳐 쪼개진 시퀀스, 한 청크 안에 여러 시퀀스) 전부 통과
- `cargo run -p syncshell-core --example osc7_check`: **실제 프로덕션 코드 경로**
  (스파이크 재현이 아니라 진짜 `TerminalSession`)로 PowerShell을 띄워 헤드리스 검증.
  5개 시나리오 전부 PASS: 초기값, 기본 cd, 드라이브 루트 cd .., 한글+공백 경로,
  응답 대기 없는 연속 cd

### 예상 밖의 발견 — TR-005에 영향

**`portable-pty`는 cwd를 명시하지 않으면 우리 프로세스의 CWD가 아니라
`%USERPROFILE%`을 기본값으로 쓴다** (`cmdbuilder.rs`의 `current_directory()`:
`cwd.or(home)`, `home = %USERPROFILE%`). 소스로 확인함. 검증 스크립트 작성 중
"터미널이 cargo run을 실행한 디렉터리에서 시작할 것"이라 잘못 가정했다가 발견.

TR-003(파일 목록)은 `std::env::current_dir()`을 시작 경로로 쓰는데, 터미널 패널은
기본적으로 `%USERPROFILE%`에서 시작한다 — **두 패널의 초기 경로가 다르다.**
TR-005에서 첫 동기화 이벤트가 발생하면 자연히 한쪽으로 맞춰지므로 동작을 막는
문제는 아니지만, TR-005 설계 시 "앱 시작 시 어느 쪽을 기준으로 맞출지"
(터미널의 %USERPROFILE% 따라갈지, 탐색기의 시작 경로로 터미널을 옮길지)를
명시적으로 정해야 한다. 아무것도 안 하면 사용자가 처음 앱을 열었을 때 두 패널이
서로 다른 위치를 보여주는 상태로 시작하게 된다.
