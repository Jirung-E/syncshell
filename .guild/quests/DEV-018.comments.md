## 추가: 탐색기 라벨(Proportional) 한글 미지원 발견 및 수정

`font_fallback.rs`의 `install_primary`가 Proportional(탐색기 라벨용) 폰트로
`["Malgun Gothic", "Segoe UI"]`만 조회하고 있었다 — 둘 다 Windows 전용이라
macOS에서는 하나도 안 걸리고 egui 기본 번들 폰트(한글 미지원)로 남는다.
즉 탐색기의 한글 폴더/파일명이 두부(□)로 보일 뻔했다.

후보에 `"Apple SD Gothic Neo"`(macOS)/`"Noto Sans CJK KR"`/`"NanumGothic"`(Linux)를
추가해서 고쳤다. 고치는 과정에서 두 가지를 더 발견:

1. **fontdb의 TTC(TrueType Collection) face 인덱스를 버리고 있었음**: macOS
   시스템 폰트 다수가 여러 굵기를 한 `.ttc` 파일에 묶어 담는데(예:
   `AppleSDGothicNeo.ttc`), `install_family`/`find_system_font_for`가
   `db.with_face_data(id, |data, _| data.to_vec())`로 face 인덱스를 버리고
   `egui::FontData::from_owned()`(항상 face 0 고정)로 등록하고 있었다. 두
   지점 다 실제 face 인덱스를 받아 `FontData { index, .. }`로 넘기도록 고침.

2. **egui `has_glyph()`가 이 폰트에 한해 신뢰 불가**: "Apple SD Gothic Neo"를
   fallback 체인의 **첫 번째(주 폰트)**로 두면, egui가 U+FFFD(replacement
   character) 글리프를 가진 첫 폰트를 그대로 "replacement face"로 채택해버리는데
   이 폰트가 U+FFFD도 갖고 있어서 그게 바로 이 폰트가 된다. 그 뒤로 `has_glyph`는
   "이 문자가 replacement face로 resolve됐는가"만 보므로, **이 폰트로 resolve되는
   모든 문자**(실제로는 멀쩡한 글리프인 '가', 'A' 포함)가 "커버 안 됨"으로
   오판된다. `glyph_width`/`layout_no_wrap`으로 직접 확인해보면 실제 렌더링은
   정상(진짜 두부는 폭 0, '가'는 폭 13.8pt의 진짜 글리프)이라 **실사용 렌더링에는
   영향 없음** — 하지만 우리 회귀 테스트가 `has_glyph`를 쓰면 이 폰트에서는 항상
   거짓 실패하므로, 테스트는 `glyph_width > 0`으로 대체했다(`font_fallback.rs`
   `proportional_font_covers_hangul`).
