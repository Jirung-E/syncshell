## 우클릭 컨텍스트 메뉴 구현 (이 퀘스트 범위 중 일부)

사용자 요청: "폴더 우클릭시 시스템 파일탐색기에서처럼 메뉴가 나와야함".

## 방향 확인

"시스템 파일탐색기에서처럼"이 두 가지로 읽혀서 먼저 확인했다:
(a) 탐색기처럼 **보이고 동작하는** 메뉴를 직접 구현, (b) **실제 윈도우 셸 메뉴**를
IContextMenu COM으로 띄우기(7-Zip·Git 등 셸 확장 항목까지 그대로).

사용자 선택: **직접 만들되, 셸 메뉴는 나중에.** 이 퀘스트의 기존 방침
("플랫폼 API를 직접 부르지 말 것")과도 일치한다. 셸 메뉴 연동은 [[DEV-017]]로 분리.

## 구현

**`syncshell-core/src/fsops.rs` (신설)** — 파일 조작. UI를 모른다(architecture 규칙).
- `rename()` — 같은 폴더 안에서 이름만. 경로 구분자를 막는 게 핵심이다:
  이름 칸에 `..\other\evil`을 넣으면 이름 변경이 아니라 **다른 폴더로의 이동**이
  돼버린다. Windows 금지문자(`: * ? " < > |`)도 공통으로 막는다(Unix에서 만든
  파일이 Windows에서 안 열리는 상황 방지). 대소문자만 바꾸는 이름 변경은
  허용해야 해서(`exists()`가 true로 나옴) 별도 처리.
- `move_to_trash()` — `trash` 크레이트. Windows 휴지통 / macOS 휴지통 /
  Linux XDG trash를 한 API로 덮는다. 되돌릴 수 있으므로 확인 대화상자 없이
  바로 실행(일반 탐색기와 같은 감각).
- `create_dir_unique()` — 이미 있으면 `새 폴더 (2)`처럼 번호를 붙인다. 새로
  만들기를 연달아 눌렀을 때 오류 대신 하나 더 생기는 게 자연스럽다.

**`syncshell-ui/src/file_panel.rs` (신설)** — 패널 UI + 메뉴. lib.rs가 길어져서 분리.
- `FileAction` 열거형으로 사용자가 고른 동작만 돌려주고, 실제 수행은 호출부가
  한다 — 터미널 주입·동기화 갱신은 패널이 모르는 자원을 건드려야 해서 여기서
  직접 하면 빌림 검사에 걸린다.
- **항목 메뉴**: 열기 / 여기서 터미널 열기(폴더만) / 이름 바꾸기 / 삭제(휴지통) / 경로 복사
- **빈 공간 메뉴**: 새 폴더 / 새로 고침 / 현재 경로 복사
- 이름 바꾸기는 `egui::Modal` 대화상자. 첫 프레임에 텍스트 칸으로 포커스가
  가고 현재 이름이 채워져 있다(확장자까지 다시 타이핑하게 만들지 않는다).
  Enter로 확정, Esc/바깥 클릭으로 취소.

**"여기서 터미널 열기"** 는 이 앱의 성격상 넣은 항목이다 — 탐색기는 그대로 두고
터미널만 그 폴더로 옮긴다. `SyncState`에도 알려줘야 터미널의 OSC7 응답을
"우리가 시킨 것"으로 인식하고 탐색기를 되돌리지 않는다.

**새 폴더를 만들면 곧바로 이름 바꾸기 대화상자가 뜬다** — 탐색기가 새 폴더 생성 후
바로 이름 편집 상태로 들어가는 것과 같은 흐름.

## 사용자 리포트 "복사/붙여넣기 작동 안함" 조사 결과

**결론: 우클릭 메뉴 경로는 실제로 정상 동작함.** 처음엔 재현 실패해서 진짜
버그인 줄 알았는데, 알고 보니 제 테스트 방법 자체가 틀렸었다(egui
`any_popup_open()`을 프레임 밖에서 확인해서 항상 false로 나옴 — 컨텍스트
메뉴 위치도 잘못 추정하고 있었음). 테스트를 실제 팝업을 진짜로 열고 그 안의
버튼을 찾아 누르는 방식으로 다시 짜서(`copy_then_paste_produces_copy_and_paste_actions_via_real_menus`)
확인해보니 우클릭 → 복사 → 우클릭 → 붙여넣기가 끝까지 정상 동작함.

**추정 원인: Cmd+C/Cmd+V 단축키가 없음.** 지금은 우클릭 메뉴로만 복사/붙여
넣기가 되고, 파일을 클릭해서 "선택"하는 개념 자체가 없다(폴더는 클릭하면
바로 이동, 파일은 더블클릭 전까진 아무 반응 없음). 아마 Cmd+C/Cmd+V를
눌러보고 "작동 안 함"이라고 느끼셨을 가능성이 높음.

**단축키를 지금 안 붙인 이유**: 터미널이 이미 Ctrl+C를 (선택 있으면 복사,
없으면 인터럽트로) 쓰고 있어서, 탐색기에도 전역 Cmd+C를 붙이면 터미널에
포커스가 있을 때 어느 쪽이 반응해야 하는지 충돌 여지가 있다. 포커스 관리를
제대로 안 하고 넣으면 터미널의 기존 Ctrl+C 동작(BUG-001에서 공들여 고친
부분)을 망가뜨릴 위험이 있어서, 확인 없이 넣지 않았다.

실사용 버그 리포트("복사/붙여넣기 작동 안함")에 이어서, 파일 선택 개념과 키보드 단축키를 추가했다.

- `FilePanelState.selected: Option<PathBuf>` — 파일(폴더 제외)을 단일 클릭하면 선택 상태로 표시되고, Cmd+C 등 단축키의 대상이 된다. 더블클릭은 기존대로 열기(OpenFile) 동작 유지(DEV-015 폴더 단일클릭 규칙과 별개).
- 단축키: macOS는 Cmd+C/Cmd+V, Windows/Linux는 Ctrl+Shift+C/V(사용자 확인: "맥이랑 윈도우, 리눅스 다 동작해야하는데, 맥은 cmd+c로 하면 충돌 없을거같고, 윈도우나 리눅스는 우선 ctrl+shift+c/v로").
- 터미널 위젯(`terminal_widget.rs`)에 이미 있던 "Ctrl+Shift+C = 항상 복사" 바인딩과 충돌하지 않도록, `Tab`에 `ActivePanel`(마지막으로 클릭한 패널이 탐색기/터미널 중 어디인지) 상태를 추가하고, 파일 패널의 단축키는 `panel_active`(탐색기가 활성 상태)일 때만 반응하도록 게이팅했다.
- 단위 테스트 추가(`file_panel.rs`): `single_click_on_file_selects_without_opening`, `copy_paste_keyboard_shortcuts_work_when_panel_active`, `keyboard_shortcuts_are_ignored_when_panel_not_active`.

부수적으로 이번 테스트 작성 중 egui 테스트 헬퍼(`click_at`)의 버그를 하나 발견/수정: 새로 생성된 위젯은 그 컨텍스트에서 처음 그려지는 프레임에는 press 이벤트의 hover 판정이 아직 안 잡혀서(레이어 순서를 모름) 클릭이 씹히는 문제가 있었음 — press/release 시퀀스 전에 이벤트 없는 "워밍업" 프레임을 한 번 추가해서 해결(실제 UI 동작과는 무관, 테스트 전용 이슈).

실제 UI로 사람이 확인해야 할 부분(자동 테스트로 못 잡음): 실제 macOS 앱에서 Cmd+C로 파일 복사가 정말 클립보드에 들어가는지, Windows/Linux에서 Ctrl+Shift+C/V가 터미널 포커스일 때 터미널의 기존 복사 동작과 안 겹치고 탐색기 포커스일 때만 파일 복사/붙여넣기로 동작하는지.
