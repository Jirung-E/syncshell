Windows에서 터미널에 키를 꾹 누르면 OS 반복 속도보다 느리게 입력되고, 키를 뗀 뒤에도 밀린 입력이 한동안 계속 들어간다. 그 사이 마우스 이동·창 크기 변경도 같이 버벅인다(앱 전체가 느림). 2026-10-04 Windows 사용자 확인, `cargo run --release`.

## 지금까지 확인한 것
- 같은 PowerShell을 Windows Terminal에서 쓰면 정상 → 셸(PSReadLine) 자체 문제 아님
- macOS에서 release 프레임 비용 실측: 터미널 그리기 0.2ms, 탐색기 0.04ms, 타이핑 중에도 1~2ms → 앱의 CPU 레이아웃 비용은 원인 아님(최소한 macOS에선)
- 코드 확인: 키 입력·PTY 출력은 프레임마다 쌓인 것을 전부 처리, `resize`는 크기 같으면 건너뜀, 프레임마다 도는 무거운 작업 없음
- 남은 후보(Windows 전용 경로): (a) 렌더러 present/vsync 대기, (b) UI 스레드의 PTY 쓰기(`write_all`)가 막힘, (c) OS 기본 ConPTY(System32) 성능 — WezTerm 등은 이 때문에 conpty.dll/OpenConsole.exe를 동봉

## 1단계: 진단 표시
`SYNCSHELL_PROFILE=1`로 실행하면 상태바에 프레임 간격·UI 처리 시간·PTY 쓰기 시간·PTY 출력량을 띄워 Windows에서 실제 수치로 원인을 가른다.

## 원인 (최종, 2026-10-11)
[[BUG-007]]과 같은 원인: 터미널이 매 프레임 `request_focus()`를 불러 egui가 매 프레임 IME 조합 중단을 요청 → egui-winit이 매 프레임 IME를 껐다 켬(`set_ime_allowed(false→true)`, Windows에선 `ImmAssociateContextEx`). 이 비용 때문에 키 반복이 밀렸다. 3760ecb(BUG-007 수정)로 해결 — Windows 실제 키보드: 30~31회/초, 떼면 바로 멈춤, 한글 입력 정상(사용자 확인 "둘다 바로 멈춘다. 한글 입력도 잘된다").

중간에 넣었던 egui-winit 패치(IME 영역 갱신 조건, vendor/egui-winit)는 패치를 끈 상태로도 정상(같은 30~31회/초)이라 필요 없어 제거했다.

## 남겨 둔 진단 도구
`SYNCSHELL_PROFILE=1`(상태바·stderr 1초 요약), `SYNCSHELL_SELFTEST=keys|oskeys`(실제 창 자가 진단, oskeys는 Windows SendInput), `SYNCSHELL_NO_IME=1`, `SYNCSHELL_NO_ACCESSKIT=1`, `input_latency_probe` 테스트(헤드리스).

## Test plan
- Windows 실제 키보드로 영문·한글 키 꾹 → OS 반복 속도, 떼면 바로 멈춤 (3760ecb에서 확인됨, vendor 제거 후 빌드로 한 번 더)
