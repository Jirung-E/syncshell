## 피드백 반영 완료

댓글 #2의 두 항목 모두 재현·수정·검증했습니다.

### 4. D 드라이브 동기화 안됨 → 수정

**원인**: `cd D:\` 후 OSC7 페이로드를 디코드하는 과정에서 세그먼트 분리 시
trailing separator가 사라져 `D:`(백슬래시 없음)로 디코드됐습니다.
Windows에서 `D:`는 드라이브 루트가 아니라 **"이 프로세스가 D 드라이브에서
마지막에 있던 위치"**를 가리키는 전혀 다른(드라이브 상대) 경로입니다 — 그게
우연히 앱을 실행한 위치였던 것이라 "탐색기가 앱 위치로 표시됨"이라는 정확히
그 증상으로 나타났습니다.

`osc7.rs`의 `decode_payload`에서 디코드 결과가 `X:` 형태(드라이브 문자만
있고 백슬래시 없음)면 `X:\`로 정규화하도록 수정. 헤드리스로 재현 후 수정
확인함 — `D:\`, `D:/`, `D:` 세 가지 입력 형태 모두 이제 `D:\`로 정확히
감지됩니다. 회귀 테스트 추가(`drive_root_decodes_with_trailing_backslash`).

### 5. 깜빡임 거슬림 → 진짜 원인을 다시 찾아서 수정

처음엔 TR-005에서 "PSReadLine이 이전 프롬프트를 한 번 더 redraw하는 것"으로
추정했는데, 원시 PTY 바이트 스트림을 직접 타이밍 측정해보니 **중복 OSC7
이벤트 자체가 없었습니다.** 진짜 원인은 제 통합 코드의 레이스였습니다:

`SyncState.user_navigated()`가 `current`를 낙관적으로 즉시 갱신하는데,
`TerminalSession.cwd`는 실제 셸 확인이 오기 전까지 옛 값 그대로입니다.
그 사이 매 프레임 `session.cwd`(아직 안 바뀐 옛 값)를 계속
`sync.terminal_cwd_changed()`에 흘려보내고 있었고, `SyncState`는 그걸
자신의 최신 `current`와 비교해서 "다르다"(진짜 변경이다)고 오판했습니다.
클릭할 때마다 "옛 폴더로 갔다가 새 폴더로 다시 감"으로 보였던 게 이거였습니다.

**수정**: `TerminalSession`에 `take_cwd_change()`를 추가 — cwd가 실제로
바뀌었을 때만, 한 번만 값을 내어줍니다. 동기화 로직은 이제 `session.cwd`를
직접 읽지 않고 반드시 이걸 통해서만 값을 받습니다. 부가적으로 실제 셸의
빠른 연속 상태 변화(진짜 중복 감지가 생기는 경우, 예: 응답 대기 없는 연속
cd)를 위해 150ms 디바운스도 같이 넣어뒀습니다 — 이건 여전히 유효한 안전장치.

`sync_check` 예제로 재검증: 클릭 후 `explorer_moves`가 완전히 비어있음(예전엔
옛 경로가 한 번 더 찍혔음) — 에코가 티끌만큼도 안 남습니다.

### 자동 재검증
- `cargo test -p syncshell-core`: 12개 전부 통과(드라이브 루트 회귀 테스트 추가)
- `cargo run -p syncshell-core --example osc7_check`: 5개 시나리오 전부 통과
- `cargo run -p syncshell-core --example sync_check`: 5개 시나리오 전부 통과,
  에코 억제 항목은 이제 "완전히 비어있음" 기준으로 엄격하게 확인

다시 한번 실사용해서 D 드라이브와 클릭 시 깜빡임이 실제로 없어졌는지
확인 부탁드립니다.

## Tab 자동완성 안 되던 것 → 수정

**예광탄에서 의도적으로 스킵한 게 아니라 단순 누락이었습니다.** TR-002 스코프에
"키 입력: 일반 문자, Enter, Backspace, 방향키, Ctrl+C"라고 적어뒀는데 Tab을
목록에 넣는 걸 깜빡했고, 코드에도 `Key::Tab` 분기가 아예 없어서 눌러도
`_ => {}`로 조용히 무시되고 있었습니다.

자동완성 자체는 PSReadLine(셸 쪽)이 처리하는 기능이라 syncshell이 구현할 건
없고, **Tab 키 바이트(0x09)를 PTY에 그대로 전달하기만 하면 됩니다.**
`terminal_widget.rs`에 한 줄 추가(`Key::Tab => 0x09 전달`)했고, 겸사겸사
Escape(0x1B)도 같이 넣었습니다 — 자동완성 메뉴를 열 수 있으면 취소도 가능해야
자연스러운 짝입니다.

### 검증
화면 없이는 실제 자동완성 동작을 눈으로 볼 수 없어서, 렌더링된 터미널
그리드를 직접 읽어 확인하는 방식으로 헤드리스 검증했습니다
(`examples/tab_check.rs`, 새로 추가): `C:\Windows`에서 `cd Sys` 입력 후
탭 바이트 전송 → 실제 PowerShell(PSReadLine)이 `cd .\System\`로 completion.
라인이 늘어나고 실제 존재하는 폴더명을 포함하는 것까지 확인했습니다 — Tab이
셸까지 정상적으로 도달해서 진짜 completion이 동작한다는 뜻입니다.

`cargo run -p syncshell-core --example tab_check` 로 재현 가능합니다.

## 2차 피드백 7건 전부 수정 완료

### 1. 폴더 이동시 절대경로 → 상대경로
직계 자식(폴더 클릭)이면 폴더명만, 직계 부모(".." 클릭)면 `cd ..`로 주입하도록
`SyncState.user_navigated`를 바꿨습니다. 드라이브를 넘나드는 등 직계 관계가
아니면 안전하게 절대경로로 폴백합니다. 실제 PowerShell로 왕복 검증함
(`examples/relative_cd_check.rs`).

### 2. exit 쳐도 앱이 안 닫히던 것 → 수정
**원인**: ConPTY는 자식 프로세스가 종료돼도 master 쪽 `read()`가 EOF를 신뢰성
있게 안 준다는 걸 실측으로 확인했습니다(`exit` 후 5초를 기다려도 EOF 안 옴 —
꽤 놀라운 ConPTY 특성입니다). `Child::try_wait()`으로 직접 폴링하는 게 유일하게
믿을 수 있는 방법이었습니다. `pump()`가 매 프레임 호출되니 거기서 폴링하고,
`session.exited`가 true면 UI가 `ViewportCommand::Close`로 앱을 닫습니다.
(`examples/exit_check.rs`로 검증)

### 3. 첫 실행시 "엔터가 이미 쳐진 것 같음" → 원인 규명 및 수정
렌더링된 그리드를 직접 덤프해서 확인해보니, 스폰 직후 화면에 **`>>`(PowerShell의
줄 연속 프롬프트)가 떠 있었습니다** — 뭔가 구문이 안 끝났다고 셸이 착각하고
있었던 겁니다. 원인: 초기화 스크립트를 주입할 때 `\r\n`을 썼는데, 실제 키보드
Enter는 `\r` 하나만 보냅니다. `\r`로 제출된 직후 남는 `\n`이 빈 줄에서 또 한 번의
Enter처럼 처리되면서 PSReadLine이 헷갈렸던 것으로 확인됨 — `\r` 하나로 바꾸니
`>>`가 완전히 사라졌습니다. 겸사겸사 `-NoLogo`도 추가해 PowerShell 저작권 배너도
없앴습니다(이것도 첫 화면이 지저분해 보이는 데 한몫했음). `cd` 주입 전체(`SyncState`)도
같은 이유로 `\r\n` → `\r`로 통일했습니다.

### 4. ls 결과가 잘리고 리사이즈해도 안 돌아오던 것 → 원인 규명 및 수정
**가장 심각했던 발견**: 터미널을 아주 좁은 컬럼 수(1컬럼)로 줄이는 걸 재현해보니
**~5GB 메모리 할당 시도 후 프로세스가 크래시**했습니다(`STATUS_STACK_BUFFER_OVERRUN`).
원인: 컬럼이 확 줄어들면 alacritty_terminal이 기존 스크롤백의 넓은 줄들을 전부 그
좁은 폭으로 리플로우해야 하는데, 줄 수가 폭발적으로 늘어나기 때문입니다.
egui가 첫 프레임에 위젯 크기를 일시적으로 아주 작게 보고하는 경우가 있어서,
이게 실사용 중 트리거됐을 가능성이 높습니다. `TerminalSession::resize()`에
최소 크기(20컬럼×4행) 하한을 걸어서 어떤 값이 들어와도 이 파국적 상황이
안 생기게 막았습니다. 완만한 범위(120→60→120)의 정상적인 리사이즈는 내용이
잘 보존되는 것도 확인했습니다.

### 5. HOME/END 안 되던 것 → 수정
Tab 때처럼 단순 누락이었습니다. Home(`ESC[H`)/End(`ESC[F`)/Delete(`ESC[3~`)를
추가하고, 실제 PowerShell에서 커서 이동이 정확히 되는지 렌더링된 라인을
읽어서 확인했습니다(`examples/homeend_check.rs`).

### 6. 링크(바로가기/심볼릭 링크) 접근 안 되던 것 → 수정
- **심볼릭 링크 폴더**: `DirEntry::file_type()`이 링크 자체의 타입을 돌려주고
  대상을 안 따라가서, 심볼릭 링크로 된 폴더가 파일로 잘못 분류돼 클릭 자체가
  안 되고 있었습니다. `path().metadata()`(대상을 따라감)로 바꿔 수정.
- **.lnk 바로가기**: 파일 열기 기능(아래 7번)으로 열면 Windows Shell이
  ShellExecute 수준에서 대상을 알아서 찾아 엽니다. 별도 파싱 불필요.

### 7. 파일 열기 안 되던 것 → 구현
TR-003에서 의도적으로 스코프 밖으로 뺐던 것(DEV-008 계획)인데, 실사용에
바로 필요해서 지금 구현했습니다. `open` 크레이트(`shellexecute-on-windows`
기능)로 기본 연결 프로그램 실행.

### 8. (추가 보고) 탭 자동완성 후 엔터 → 다른 명령이 끼어들어 실패
**원인**: 사용자가 터미널에 타이핑 중(제출 전)일 때 탐색기 클릭으로 인한 cd
주입이 그 사이에 끼어들면서, 타이핑 중이던 줄에 주입 문자열이 섞여 명령이
깨졌습니다. 이건 TR-005 계획에 "알려진 한계"로 적어뒀던 것인데, 실사용에서
실제로 명령 실패를 유발할 만큼 disruptive해서 지금 고쳤습니다.

`TerminalSession`에 `write_keyboard_input()`(실제 키보드 입력 전용 — 순수
Enter가 아니면 "아직 제출 안 함"으로 표시)과 `has_pending_user_input()`을
추가했습니다. 탐색기 클릭 시 이 상태면 cd 주입을 큐에 대기시키고, 사용자가
Enter(또는 Ctrl+C 등)로 줄을 끝낼 때까지 기다렸다가 보냅니다. 정확히 이
시나리오(타이핑 중 탭 완성 → 그 시점에 클릭 발생 → 큐잉 확인 → 제출 후에야
전송)를 헤드리스로 재현·검증했습니다(`examples/pending_input_check.rs`).

## 탭 자동완성 후 엔터 문제 — 진짜 원인 찾음 (이전 수정은 다른 버그였음)

이전 라운드에서 "타이핑 중 탐색기 클릭이 끼어든다"는 시나리오로 고쳤던 건
**실재하는 다른 버그**였지만(그건 그것대로 유효한 수정), 사용자가 다시 보고한
현상의 진짜 원인은 따로 있었습니다. 재현 조건을 다시 여쭤봐서 확인:
**"탐색기에서 폴더를 클릭한 적이 없는데, 탭을 치면 탐색기쪽 폴더가 선택되고
그 상태에서 엔터를 치면 그 폴더로 cd가 입력되어버림."**

### 진짜 원인 — PTY 타이밍이 아니라 egui 포커스 시스템

터미널 위젯이 키보드 포커스를 명시적으로 요청한 적이 없었습니다. egui는
"포커스를 가진 위젯이 하나도 없으면 Tab/화살표 키를 자동으로 '다음 위젯으로
포커스 이동' 명령으로 소비한다"는 내부 규칙이 있습니다(egui 소스
`memory/mod.rs`에서 직접 확인: `Key::Tab if !modifiers.any() => Some(FocusDirection::Next)`,
그리고 이 규칙은 현재 포커스를 가진 위젯이 스스로 "이 키는 내가 쓸게"라고
선언(`EventFilter`)하지 않는 한 항상 적용됩니다).

그래서 실제로 벌어진 일:
1. 사용자가 터미널에서 Tab을 누름 (PTY로는 정상 전달돼 자동완성도 잘 됨)
2. **동시에** egui가 이 Tab을 "포커스 이동" 명령으로도 소비 → 포커스가 왼쪽
   탐색기의 `selectable_label`(폴더 항목)로 옮겨감
3. 사용자가 Enter를 누름 (PTY로는 정상 전달돼 자기 명령이 제출됨)
4. **동시에** egui가 "포커스를 가진 위젯에서 Enter = 그 위젯 활성화(클릭)"로
   해석 → 포커스를 갖고 있던 그 폴더 항목이 "클릭됨" 처리되어 `cd` 주입 발생

두 가지(터미널로의 정상 전달 + 탐색기 위젯의 오작동 활성화)가 **동시에** 일어나서
"내가 타이핑한 것도 되고, 엉뚱한 cd도 같이 들어온다"는 정확히 그 증상이었습니다.

### 수정
`TerminalWidget`이 매 프레임 `response.request_focus()` + `set_focus_lock_filter()`로
Tab/화살표/Esc를 스스로 소비하겠다고 선언하도록 했습니다. 파일 패널에서 클릭 등으로
포커스가 잠깐 옮겨가더라도, 터미널이 CentralPanel(파일 패널보다 나중에 그려짐)에서
매 프레임 다시 가져오므로 항상 터미널이 포커스를 유지합니다.

### 검증
egui의 헤드리스 실행(`egui::Context::run_ui`)으로 GPU/윈도우 없이 정확히 같은
위젯 구조(SidePanel의 selectable_label + CentralPanel의 포커스 고정 로직)를
재현해서, Tab → Enter 시퀀스가 SidePanel 항목을 잘못 활성화하는지 확인했습니다.

**수정 코드를 일부러 빼고 먼저 돌려봤더니 정확히 실패했습니다** (탐색기 항목이
"클릭됨"으로 나옴) — 진단이 정확했다는 직접적인 증거입니다. 수정을 다시 넣으니
통과. 이 테스트를 `syncshell-ui`에 영구 회귀 테스트로 남겨뒀습니다
(`terminal_widget::tests::tab_then_enter_does_not_activate_sidepanel_item`).

### 자동 검증 현황
- `cargo test -p syncshell-ui`: 1개 (신규 포커스 회귀 테스트) 통과
- `cargo test -p syncshell-core`: 16개 전부 통과 (변경 없음, 회귀 없음 확인)
- 전체 워크스페이스 빌드 정상, 실행 파일 스모크 테스트 통과

이번엔 실제 원인을 egui 소스 레벨에서 확인하고 헤드리스로 재현까지 했으니
확실합니다. 다시 확인 부탁드립니다.

## "ls 결과가 잘림" — 진짜 원인은 렌더러 wrap 버그가 아니었습니다

### 결론부터
이전에 고친 **"극단적으로 좁게 리사이즈하면 크래시"** 는 별개의 진짜 버그였고
잘 고쳐졌습니다. 하지만 **"여전히 잘린다"는 이번 증상의 근본 원인은 다릅니다**:
**터미널 패널이 기본 창 크기 기준으로 너무 좁아서, PowerShell의
`Get-ChildItem`/`ls` 기본 테이블 포맷터가 폭이 부족하면 이름(Name) 컬럼을
통째로 드롭해버리는 PowerShell 자체의 동작**이었습니다. 이건 실제 Windows
Terminal에서도 같은 폭이면 똑같이 일어나는, syncshell 렌더러의 결함이 아닙니다.

### 검증 방법
실제 프로덕션 코드(`TerminalWidget::show`가 매 프레임 `session.resize()`를 호출하는
것까지 포함)를 egui 헤드리스 실행(`Context::run_ui`)으로 실제 PTY와 함께 반복
구동하는 테스트를 새로 작성했습니다(`syncshell-ui`에 추가, GPU/윈도우 불필요).

1. **순수 텍스트(Write-Host)는 정상적으로 wrap됨을 먼저 확인** — 40컬럼 터미널에
   80글자를 출력하면 alacritty_terminal이 정확히 두 줄로 나눠 그리고 `WRAPLINE`
   플래그도 정확히 찍힘. **렌더러/모델 레벨 wrap 자체는 문제없음.**
2. **cols 값이 프레임마다 안정적인지 확인** — 리사이즈 스래싱(제 첫 가설)은
   기각됨. 50~80프레임 동안 단 하나의 값으로 고정.
3. **실제 `Get-ChildItem C:\Windows`를 47컬럼(700px 폭 시뮬레이션)에서 실행** →
   화면에 Mode/Date/Time/Size는 나오는데 **파일 이름 컬럼이 통째로 안 보임.**
4. **같은 명령을 95컬럼(1400px)에서 재실행** → 파일 이름이 전부 정상적으로 보임

   나타나거나 사라짐 — 이건 wrap 실패가 아니라 PowerShell이 폭에 따라
   "표시할 컬럼 자체를 선택"하는 동작임을 확정.**

### 조치
`Get-ChildItem`이 필요로 하는 최소 폭에 못 미치는 게 실사용에서 자주 걸리는
원인이라, **기본 창 크기를 1000×640 → 1400×800으로 넓혔습니다.** 파일 패널
(기본 320px)을 뺀 나머지가 넉넉해져서 이 PowerShell 동작을 덜 만나게 됩니다.
근본적으로는 폰트가 완전한 monospace가 아니라 셀 폭을 넓은 문자('M') 기준으로
잡는 것도 컬럼 수를 실제보다 적게 만드는 요인인데, 이건 DEV-011(폰트 폴백
체인 제대로 구현)에서 다룰 사안으로 남겨둡니다.

## Shift+Tab 안 먹힘 → 수정

**원인**: `terminal_widget.rs`의 키 매칭이 `egui::Key::Tab if !modifiers.shift`
조건으로 **일반 Tab만** 바이트를 전달하고 있었습니다. Shift+Tab은 이 조건에
안 걸려서 `_ => {}`로 빠지며 아무것도 전송되지 않았습니다 — 처음 Tab을
구현할 때 "일단 일반 Tab만"으로 좁혀놓고 Shift+Tab 케이스를 채워 넣는 걸
빠뜨린 것이었습니다.

**수정**: Shift+Tab에 CBT(Cursor Backward Tabulation, `ESC[Z`) 시퀀스를
추가했습니다. PSReadLine은 이 시퀀스를 "이전 자동완성 후보로 되돌아가기"로
해석합니다.

### 검증
`examples/tab_check.rs`에 시나리오 확장: `C:\Windows`에서 `cd Sys` + Tab →
`System`, Tab 한 번 더 → `System32`, **Shift+Tab → 다시 `System`으로 정확히
역순환**하는 것을 실제 PowerShell로 확인했습니다.

- 전체 워크스페이스 빌드 정상

## 선제 점검 — 붙여넣기(Ctrl+V)가 전혀 동작하지 않고 있었음

Shift+Tab 확인 요청에 "더 확인할 거 없는지" 질문을 받고, 지금까지 나온 패턴
(Tab/Shift+Tab/Home/End/Delete가 하나씩 빠져있던 것)을 감안해 키/입력 처리
코드를 다시 훑어봤습니다.

**발견**: `terminal_widget.rs`의 입력 처리가 `egui::Event::Text`와
`egui::Event::Key`만 매치하고 있었고, **`egui::Event::Paste`는 아예 없어서
`_ => {}`로 빠지고 있었습니다.** 즉 Ctrl+V, 마우스 중클릭 붙여넣기 등이
지금까지 전혀 동작하지 않았을 것입니다 — 터미널에서 매우 자주 쓰는 동작이라
다음 버그 리포트로 나올 가능성이 가장 높다고 판단해 먼저 고쳤습니다.

### 수정
- `Event::Paste(text)` 매치 추가, 텍스트를 그대로 PTY에 전달.
- 여러 줄을 붙여넣으면 내부 개행이 `\n`으로 들어오는데, 이 코드베이스는
  줄 끝을 `\r` 하나로 통일하기로 확정했었습니다(첫 실행 시 `>>` 잔상 버그의
  원인이 `\r\n` 사용이었던 것 — 앞선 댓글 참고). 같은 문제가 재발하지 않도록
  붙여넣은 텍스트의 `\n`을 `\r`로 정규화합니다.
- bracketed paste 모드는 여전히 범위 밖(TR-002 "생략") — 원본 텍스트를
  그대로 전달만 합니다.

### 검증
실제 프로덕션 위젯(`TerminalWidget::show`)에 `Event::Paste`로 두 줄
(`"cd C:\Windows\ncd System32\n"`)을 합성 주입하고, 실제 PowerShell로
두 `cd`가 순서대로 정확히 처리되어 최종 `C:\Windows\System32`에 도달하는지
확인했습니다(`pasted_multiline_text_executes_each_line` 테스트로 영구 회귀
테스트화).

### 자동 검증
- `cargo test -p syncshell-ui`: 3개 전부 통과 (신규 붙여넣기 테스트 포함)
- `cargo test -p syncshell-core`: 16개 전부 통과 (회귀 없음)
- 전체 워크스페이스 빌드 정상

## 컴파일이 느린 이유 — D: 드라이브가 exFAT

**원인 확정**: `D:` 드라이브가 **exFAT**로 포맷돼 있습니다 (`Get-Volume D` 확인).
exFAT은 하드링크를 지원하지 않는데, rustc의 증분 컴파일 캐시는 하드링크에
크게 의존합니다. 그 결과 이 세션 내내 모든 빌드에서 "hard linking files in
the incremental compilation cache failed. copying files instead" 경고가
떴었습니다 — 매번 파일을 하드링크 대신 통째로 복사해야 해서 느렸던 것입니다.

### 조치
소스 코드는 `D:`에 그대로 두고, **빌드 산출물(target 디렉터리)만 NTFS인
`C:`로 옮기도록 `.cargo/config.toml`을 추가**했습니다:
```toml
[build]
target-dir = "C:/Users/User/.cargo-targets/syncshell"
```
`cargo build`/`cargo run` 등은 전과 똑같이 쓰면 되고, 내부적으로만 빌드 결과물
위치가 바뀝니다. 비파괴적이고 되돌리기 쉬운 변경입니다(설정 파일만 지우면
원래대로).

### 효과 확인
- 새 target-dir로 전체 빌드(1회, 캐시 없음): 1분 28초
- 파일 하나 touch 후 증분 빌드: **6.7초**, 하드링크 경고 완전히 사라짐
- `cargo run`이 새 위치에서 정상 동작하는 것도 확인함(예제 실행 성공)

### 되돌림
C: 드라이브에 여유 공간이 부족하다고 하셔서 **이 변경은 되돌렸습니다** —
`.cargo/config.toml` 제거, C:에 만들었던 target 디렉터리(2.2GB)도 삭제.
지금은 원래대로 `D:\...\target`을 그대로 쓰고 있고, exFAT 하드링크 미지원
경고도 다시 뜹니다(원상복구 확인함).

**진단 자체는 유효하니 참고용으로 남김**: 나중에 C:나 다른 NTFS 위치에
여유 공간이 생기면 같은 방법(`target-dir` 설정)으로 다시 시도해볼 수 있음.

## 별개 확인 — 심볼릭 링크 테스트가 스킵된 이유 재검토

앞서 `symlinked_folder_is_classified_as_dir` 테스트가 "심볼릭 링크 생성 권한
없음(Developer Mode 확인 필요)"로 스킵됐던 것을, 그때는 권한 문제로 추정했는데
**exFAT은 심볼릭 링크 자체를 지원하지 않으므로** 사실 이게 더 유력한 원인일
수 있습니다. 코드 수정(`file_type()` → `path().metadata()`)의 정당성 자체는
Rust 표준 문서 동작 차이에 근거하므로 변함없지만, 실제 심볼릭 링크 종단 검증은
NTFS 드라이브에서 한 번 확인해볼 가치가 있습니다.

# 예광탄 회고 결론

TR-001~005를 순서대로 구현하고, 사용자가 실제 워크플로우(폴더 이동, ls,
Tab 자동완성, 붙여넣기, exit 등)로 실사용하며 총 10건 이상의 버그를 리포트 →
재현 → 수정 → 검증하는 사이클을 거쳤다. 아래는 스파이크 시점에 정해뒀던
5가지 평가 질문에 대한 결론.

## 1. OSC7 방식이 실전에서 버티는가
**버틴다, 단 주변 코드의 완성도가 관건이었다.** OSC7 감지 자체(파싱, 디바운스,
드라이브 루트 처리)는 처음부터 견고했다. 실사용에서 드러난 문제들은 OSC7
메커니즘 자체가 아니라 **그 위에 얹은 동기화 로직의 레이스 컨디션**이었다:
- `session.cwd`를 매 프레임 재통지하며 낙관적 업데이트와 충돌 → 클릭 시
  탐색기가 옛 폴더로 튀는 버그 (→ `take_cwd_change()` 도입으로 수정)
- 사용자가 타이핑 중(제출 전)에 탐색기 클릭이 끼어드는 문제 (→
  `pending_user_input` 추적 + 큐잉으로 수정)
- 드라이브 루트("D:" vs "D:\\") 디코딩 버그 (→ 정규화 추가)
결론: **OSC7은 신뢰할 수 있는 기반이지만, "감지됐다"와 "안전하게 반영해도
된다"는 별개의 문제이고 후자가 훨씬 까다로웠다.**

## 2. core / ui 분리가 실제로 지켜졌는가
**지켜졌다.** `syncshell-core`의 Cargo.toml과 소스 전체에 egui/eframe 참조가
전혀 없음을 최종 확인(grep으로 재검증). PTY, OSC7, 동기화, 파일시스템 로직
전부 UI 프레임워크 독립적으로 남아있어, 2·3단계(WSL/Linux/macOS) 이식 시
core는 그대로 재사용 가능한 상태.

## 3. egui 셀 그리드 렌더러 성능이 실용적인가
**실용적이다.** 세션 내내 사용자가 렌더링 "느림"이나 "끊김"을 보고한 적이
없었다 — 리포트된 문제들은 전부 기능 누락(Tab, Paste, Home/End)이나 로직
버그(포커스, 레이스)였지 렌더링 성능 문제가 아니었다. 다만 알아낸 위험:
**터미널을 극단적으로 좁게 리사이즈하면 alacritty_terminal이 스크롤백을
리플로우하다 ~5GB 메모리 할당 후 크래시**하는 것을 발견 — `MIN_COLS`/`MIN_ROWS`
하한으로 막아뒀다. 이건 렌더러 "성능"이 아니라 "안전 경계" 이슈였다.
egui를 고른 근거(콜드 스타트, 메모리) 자체를 재검토할 이유는 없었다.

## 4. 동기화가 실제로 편한가
**개념은 편하고, 구현이 성숙하면서 편해졌다.** 초기에는 여러 버그(레이스,
포커스 스틸링, 입력 끼어들기) 때문에 오히려 방해가 됐지만, 하나씩 고치면서
사용자가 "동기화 자체가 불편하다"는 피드백을 준 적은 없었다 — 전부 구현
결함에 대한 피드백이었다. 온/오프 토글의 필요성은 이번 세션에서 드러나지
않았음(향후 필요해지면 그때 추가).

## 5. 콜드 스타트 시간
이번 세션에서 정량적으로 측정하진 않았으나, 사용자가 시작 속도에 대한
불만을 제기한 적이 없다.

## 발견된 재사용 가능한 교훈 (아키텍처 규칙에 반영)
- ConPTY는 자식 프로세스 종료 시 read() EOF를 신뢰성 있게 주지 않는다 —
  `Child::try_wait()` 폴링이 유일하게 확실한 방법.
- PTY에 쓰는 줄 끝은 반드시 `\r` 하나만 — `\r\n`은 PSReadLine이 연속줄
  프롬프트를 잘못 띄우게 만든다.
- 터미널을 아주 좁게(수 컬럼 이하) resize하면 alacritty_terminal이 파국적
  메모리 할당을 시도할 수 있다 — 최소 크기 하한이 필수.
- egui에서 포커스를 가진 위젯이 없으면 Tab/화살표가 전역 포커스 이동으로
  소비된다 — 키보드 중심 위젯(터미널)은 매 프레임 명시적으로 포커스를
  요청하고 EventFilter로 해당 키를 잠가야 한다.
